# taxonomy-spec-k12

**Kind:** planning

## Goal

Write the design down and reconcile the ADR set, so `02`–`05` implement from a
written spec rather than from this node's brief. Settle the two questions the
brief lists as still open.

## Context

- The node brief's **Decisions** section is the input. This leaf turns it into
  a spec plus reworked ADRs; it does not re-litigate it.
- ADR *task-kind-taxonomy* — its central claim is "a closed set of **five**",
  with a "Why the set is closed" argument and a "Considered options" entry
  rejecting a free-text label. Seventeen kinds does not weaken that argument
  (the set is still closed, still enumerable, still inheritable by
  `leaf-decompose`) but every count in it is wrong and the discipline table is
  incomplete.
- ADR *model-per-task-kind* — carries the **no-fallback** rule and rejects
  fallback chains outright. The family axis needs that rule carved, not deleted:
  the reason it exists (never pick a model for a kind the user never configured)
  still holds *across* kinds.
- `linkuistics:decision-records` for the rework discipline; `SPEC-FORMAT.md`
  for the spec's shape and the membership/grain rules.

## Done when

- `docs/specs/task-kind-taxonomy.md` exists and states: the seventeen kinds,
  each one's **discipline** and **HITL/AFK** mark, the two patterns (review
  chain, vendor pair) and their differing character, and the two routing

- Both ADRs are reworked **in place** — no superseding record, no `status:` line

- The spec passes the membership test: would a session on an unrelated future

  belongs in this node's brief instead and dies with `.grove/`.

## Decisions (running log)

**Grammar: documented only.** No enum-level relation between kinds, no
validation, no lint. The brief's stated reason (mutable positions defeat
sibling-order validation) is true but secondary; the load-bearing reason is that
a grammar *is* a relation between leaves, and this node already banked "grove
expresses no relation between leaves" when it rejected "the reviewer must not be
the author". Enforcing one would also gate, which constraint 5 forbids. A
non-blocking **lint** was raised as a genuine third option and rejected: it would
fire on a tree the human deliberately shaped, demand no action, and re-trigger on
every `leaf-insert`. The two patterns are conventions the user composes by hand;
the only machinery is the flat closed set plus routing.

**HITL/AFK is generated by a rule, and the mark predicts rather than permits.**
The rule: *a kind is HITL when a human's own words are the session's input or its
deliverable* — not "a human would want to read the output", which is true of
everything and which git already serves. That yields two HITL kinds:
`requirements` (the requirements are the human's; nobody else can supply them —
this is where the grilling went) and `prototype` (the deliverable is the reaction
it provokes). Everything else is AFK, and **`planning` flips** — stripped of
grilling, "given the design, cut vertical slices" is something `driving.md`
already equips an agent to do alone.

Crucially the mark is a **default expectation, not a gate**: *any* kind may stop
and ask a human — `design` in particular often will — and doing so is always
legitimate, never a fault. HITL means the session *cannot* complete unattended by
construction; AFK means it *normally* can. Neither mark permits or forbids
anything, and grove has no machinery behind either (as *task-kind-taxonomy*
already says of the five-kind table).

Cost accepted: `content/SKILL.md`'s Execute step no longer opens `planning` with
a grilling session — that sentence moves to `requirements`. `planning` keeps the
methodological force (sole Execute branch, the only kind that grows the tree).

**Routing precedence is harness-major.** Model resolution is four keys, in
order: `GROVE_<HARNESS>_<KIND>_MODEL` > `GROVE_<HARNESS>_<FAMILY>_MODEL` >
`GROVE_<KIND>_MODEL` > `GROVE_<FAMILY>_MODEL`. The reason the harness axis
outranks the kind axis is that they are different *kinds* of constraint: the
harness axis is a **correctness** axis (a codex profile name is garbage to pi —
`model_for`'s own words), while the kind axis is a **preference** axis (a
family's model is less specific but still the user's, and still valid for that
binary). Kind-major would let a set `GROVE_CODEX_REVIEW_MODEL` lose to an
unscoped `GROVE_REVIEW_IMPL_MODEL` written with claude in mind — the exact
failure the harness axis exists to prevent. It also composes with the existing
reroute rule: a rerouted launch consults no unscoped var, so the lattice
truncates to keys 1–2 rather than reordering.

Harness override has no harness axis (scoping a harness choice by harness is
meaningless), so it stays two keys: `GROVE_<KIND>_HARNESS` >
`GROVE_<FAMILY>_HARNESS`.

Honest surface count: **95** vars (17 kinds × 5, plus 2 families × 5), not 85.

**`work` → `impl` compatibility (banked, derived from the existing gate/degrade
asymmetry).** `**Kind:** work` in a live task file reads **silently** as `impl` —
it is the previous spelling, not a typo, so a warning would be noise on a correct
file. `--kind work` on a grow verb is **refused**, with an error naming the
replacement rather than only listing the seventeen. The read-degradation target
moves from `work` to `impl`.

**No defaults: a kind with no resolvable model var fails loudly.**
*model-per-task-kind*'s current rule — *unset ⇒ no `--model` flag, session
inherits the user's own default* — is **inverted**. An unconfigured kind is a
configuration bug, not a graceful degradation; the old rule fails *toward* the
harness default, which is still grove deciding, only less visibly. Chosen
**always** (reading (a)), not gated on opt-in (reading (b)): the user wants the
configuration explicit, and the stamp-plus-env should fully determine the launch
with nothing implicit behind it.

This also dissolves the `GROVE_WORK_*` migration question entirely — no warning,
no alias, no deprecation window. `GROVE_IMPL_MODEL` is required, so its absence
errors, and that error *is* the migration signal.

Consequences to state honestly in the ADR rework:
- A grove cannot run until every kind it reaches resolves a model var — roughly
  **9** for full coverage (7 standalone kinds + 2 family vars).
- `grove do` on a fresh repo needs `GROVE_PLANNING_MODEL` before `root-init`,
  since the `start` path is planning by construction.
- **The zero-subprocess fast path dies.** `resolve_launch`'s
  `!any_harness_override_env() && !any_model_env(stamped)` short-circuit cannot
  survive a requirement that must be checked every iteration; the kind peek now
  runs unconditionally on the `continue` path. *model-per-task-kind*'s
  "otherwise the launch is byte-for-byte the pre-feature one" consequence is
  deleted.
- `KindPeek::Empty` (the finish-cycle iteration) stays exempt — no leaf means no
  task to require a var *for*, which is not a default.
- `KindPeek::Degraded` now bails **always**, not only when a harness override is
  configured.
- Two things stay soft, explicitly: **harness absence is fine** (no
  `GROVE_<KIND>_HARNESS` means the stamped harness, and the stamp is an explicit
  binding recorded on disk, not a default), and a harness whose `model_args` is
  **empty is exempt** (it has opted out of model selection; requiring a flag it
  cannot pass would make it unlaunchable).

## Notes

The grain rule matters here: the spec describes *how the area works* and
**cites** the ADRs rather than restating them. Restate one and the two sets will
drift, after which neither binds.

Seventeen disciplines is a lot of prose to write well. If the spec turns into
seventeen thin paragraphs saying the same thing with different nouns, that is
evidence the parameterisation is too fine — surface it rather than padding,
since a kind that cannot justify a distinct discipline is precisely what
*task-kind-taxonomy* says should not exist.
