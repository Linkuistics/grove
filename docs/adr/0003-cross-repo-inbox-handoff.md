# Cross-repo inbox writes target the destination repo's `.grove-meta/` worktree; path discovery is out of scope for v1

A grove session in repo A that wants to capture an observation belonging to a grove `Y` in repo B writes to `<repo-B>/.grove-meta/inboxes/Y/...` — the same gesture as a same-repo write, against repo B's `grove-meta` worktree on disk. The rule requires repo B to be checked out locally with its `grove-meta` worktree materialised; **how** the writer locates that path (user config, CLAUDE.md hint, workspace convention) is deliberately left unspecified for v1.

## Status
superseded by ADR-0031 `0031-shed-machinery-keep-self-extension-core-and-methodology.md` — cross-repo inbox handoff is removed with the inbox / `grove-meta` subsystem.

## Why this is the same write as same-repo capture
The inbox-model ADR (`0002-grove-meta-branch-and-inbox-model.md`) defines capture as a write to `<repo>/.grove-meta/inboxes/<name>/...` via the `grove inbox` verb (the original "one file per grove" shape is superseded by the directory-per-grove shape of ADR-0004; the cross-repo argument is unaffected). Cross-repo capture is the identical operation with `<repo>` resolved to a different path on the same disk. There is no second mechanism, no second format, no second routing layer; the cross-repo case reduces to the same-repo case the moment the writer knows the target path. Reusing the local-worktree gesture also reuses every property the inbox model already earns — walk-away-ability, CLI-mediated correctness, drain-as-bootstrap — without restating any of them here.

## Why repo-path discovery is deliberately out of scope for v1
"Given grove `Y`, find repo B on disk" is the kind of mechanism that bakes badly. A config file commits the user to one workspace layout; a CLAUDE.md hint scales poorly across a team; a hardcoded `~/repos/<name>` convention assumes a directory shape that varies between humans and machines. The convention's rule is narrow on purpose: *if you can reach the path, the write is identical to a same-repo write.* How you reach it is left to user config, ad-hoc CLAUDE.md notes, or whatever convention emerges from real use, until enough usage shows which mechanism actually fits. Specifying it now would almost certainly be either wrong or unnecessarily constraining.

## Why this is the weakest of the four BRIEF use cases
The grove BRIEF's done-when required the convention to handle four cases: deferred-future, parallel-grove handoff, multi-source aggregation, and cross-repo. The first three are fully covered by the inbox model alone. Cross-repo is covered only *conditionally* — when repo B is checked out locally and its `grove-meta` worktree exists. When either precondition fails, capture from repo A cannot land in repo B today. The convention does not pretend otherwise: the CLI either succeeds against an existing local target or it fails loudly. A follow-up grove for repo-path discovery (and possibly remote-target handling) is a likely seed candidate; recording the gap here is how the BRIEF's "shown to handle" requirement is satisfied honestly rather than by overclaiming.

## Considered alternatives

**Layered F1+F2 (with a pending-cross-repo bucket).** Keep the inbox model for same-repo writes (F1); add a second mechanism (F2) — a "pending cross-repo" bucket somewhere local, e.g. `~/.grove/pending/`, that holds writes addressed to repos not currently reachable, to be reconciled when the target appears. Rejected because it doubles the surface area, introduces a second format with its own drain semantics, and creates a reconciliation step with no obvious owner. The honest "fails loudly if the target is unreachable" behaviour is simpler and does not lie about delivery.

**Shared global store at `~/.grove-meta/`.** One inbox tree per user, outside any repo, holding seeds and inboxes addressed to every grove the user works on across every repo. Rejected because it abandons walk-away-ability at the level that matters: the observations are no longer in the repo whose work they concern, so a teammate cloning repo B sees nothing, and `git log inboxes/Y.md` becomes invisible to anyone but the original author. It makes the cross-repo case trivial only by making every other case worse.

**Separate coordination repo per project (`grove-meta.git`).** Clone a second repo alongside repo B, holding what the `grove-meta` branch holds today. Already rejected for the same-repo case in ADR-0002; rejecting it here is a corollary. Cross-repo capture would still require the target's coordination repo to be present locally, so the discovery problem is unchanged — only the number of repos to clone has doubled.

**Out-of-scope deferral.** Declare cross-repo capture unsupported in v1 and address only BRIEF cases 1–3. Rejected because the same-repo mechanism *already* supports cross-repo writes whenever the target repo is reachable; refusing to acknowledge that would be artificial. The "weakest coverage within its preconditions" framing above is the honest middle path — document the case as handled where the preconditions hold, and flag the gap where they don't.
