# Portable codebase-memory skill — design

**Date:** 2026-07-29
**Status:** approved, not yet implemented

## Context and goals

The user drives three harnesses — Claude Code, Codex, and Pi — plus Gemini as a
fourth skills target. A session auditing MCP configuration across them surfaced
the real constraint: **MCP is the least portable layer in the stack.**

- Claude Code supports MCP, with tools deferred behind `ToolSearch`.
- Codex supports MCP, in a different config dialect (`config.toml`), with
  per-tool `approval_mode`.
- Gemini supports MCP.
- **Pi refuses MCP by design.** Its README's Philosophy section: "*No MCP.*
  Build CLI tools with READMEs (see Skills), or build an extension that adds MCP
  support." `docs/usage.md` repeats it — pi "intentionally does not include
  built-in MCP, sub-agents, permission popups, plan mode, to-dos, or background
  bash."

So a capability delivered as an MCP server reaches three of four harnesses and
requires three separate config dialects to do it. What travels to all four is a
**skill plus a CLI**: `SKILL.md` is a shared open format that `install.sh`
already symlinks into codex, gemini and pi, and a binary with a `cli`
subcommand runs identically under all of them.

`codebase-memory-mcp` happens to ship both halves. It exposes the same fourteen
tools over MCP *and* over `codebase-memory-mcp cli <tool> '<json>'`. There is no
capability the MCP surface has that the shell surface lacks. That makes it the
one capability that unifies across all four harnesses for free — provided the
shell form is documented well enough to use.

### Secondary goal: composition

Beyond reach, the shell form buys composition. Three independent lines of
evidence say agents that write code outperform agents that chain tool calls:

- **Anthropic, *Code execution with MCP*** (Nov 2025) — a two-server workflow
  drops from 150,000 tokens to 2,000 (98.7%) when intermediate results stay in
  the execution environment instead of transiting context.
- **Cloudflare, *Code Mode*** (Apr 2026) — 2,500 API endpoints go from 1.17M
  tokens to ~1,000 by exposing `search()`/`execute()` over a typed SDK.
- **CodeAct** (ICML 2024, Wang et al., arXiv 2402.01030) — across 17 LLMs on
  API-Bank and M3ToolEval, code actions beat JSON tool-calling by up to 20
  percentage points on success rate, using ~30% fewer turns.

Grove cannot adopt the strong form of this pattern: those designs assume you own
the agent loop, and grove does not — the harnesses do. But the pattern needs only
two ingredients, capabilities reachable from code and an execution environment,
and **every harness already ships the second one: bash**, already constrained by
each harness's existing permission and sandbox settings. Grove supplies the
first, and gets most of the composition benefit for zero new infrastructure.

## Decisions

- **One skill, `using-codebase-memory`,** in `plugins/linkuistics/skills/`.
  Gerund-prefixed to match the existing `using-jujutsu` house style.

- **Distinct slug, deliberately.** `~/.claude/skills/codebase-memory/` already
  exists and is *managed by the codebase-memory-mcp installer* — it is
  regenerated by `codebase-memory-mcp install`/`update`, so any hand-edit to it
  is temporary. Durable content must not live in a file another tool owns. The
  grove skill takes a different name so both can coexist in Claude Code without
  collision, and so grove is the single source across all four harnesses.

- **The skill documents the CLI form as the portable path,** with a short note
  on when to prefer MCP where it exists.

- **No wrapper CLI, no scripts library.** Considered and rejected: a grove
  wrapper is new code to maintain and needs wiring per capability; a scripts
  library needs curating or it rots. The skill alone carries the knowledge, and
  bash carries the composition.

## Skill content

Every claim below was verified against `codebase-memory-mcp 0.8.1` before this
document was written. The skill must cover:

1. **Invocation** — `codebase-memory-mcp cli <tool> '<json>'`, all fourteen
   tools (`index_repository`, `index_status`, `list_projects`, `delete_project`,
   `search_graph`, `search_code`, `trace_path`, `detect_changes`, `query_graph`,
   `get_graph_schema`, `get_code_snippet`, `get_architecture`, `manage_adr`,
   `ingest_traces`).

2. **`project` is required — this leads.** The CLI does *not* infer the project
   from the working directory. Running inside an indexed repo without the
   parameter still returns `{"error":"project not found or not indexed"}`.
   Project names come from `list_projects` and are path-derived, e.g.
   `Users-antony-Development-herdr`.

3. **Streams** — logs (`level=info msg=mem.init …`) go to **stderr**, JSON goes
   to **stdout**. `| jq` is therefore clean with no redirection needed.

4. **Exit codes are honest** — 0 on success, 1 on error (bad tool name,
   malformed JSON, unknown project). `set -euo pipefail` and `||` guards work.
   Note for the skill author: verify exit status *without* a pipeline, or `$?`
   reports the last pipeline stage rather than the binary.

5. **Errors are informative** — the failure payload carries `hint` and
   `available_projects`. Read it rather than discarding it.

6. **Composition patterns** — the reason the skill exists. Worked bash examples
   of the shapes that cost many round-trips as individual tool calls and one
   script as a pipeline: the high-fan-in sweep, and the trace-each-result loop.

7. **Which surface to use — stated by capability, not by harness.** One rule,
   which the reading agent resolves for itself without knowing what harness it
   is running in:

   > If the MCP graph tools are available to you, prefer them for single
   > queries — typed arguments, no shell quoting. Use the CLI when composing,
   > batching, or when those tools are not available.

   Phrasing it this way keeps the skill genuinely portable: it contains no
   per-harness branching, yet still steers an agent that *has* typed tools away
   from hand-building JSON in argv, which is where shelling out actually breaks.
   One harness-specific fact is worth stating because it is invisible otherwise:
   in Claude Code these MCP tools are deferred and must be loaded via
   `ToolSearch` before they can be called at all.

8. **Fallback** — an unindexed project is not an empty graph. Run
   `index_repository`, or fall back to Grep; do not report "no results".

## Distribution

No new mechanism. The skill lands in `plugins/linkuistics/skills/` and rides the
existing path:

- `install.sh` symlinks it into `~/.codex/skills`, `~/.gemini/skills` and
  `~/.pi/agent/skills`, exactly as it does the other fifteen skills.
- Claude Code picks it up through the `linkuistics@linkuistics` marketplace
  plugin.
- Because the targets are symlinks, a later `git pull` updates the content in
  place; `install.sh` only needs re-running when skills are added or removed.

## Testing

Every command that appears in the skill is executed against a real indexed
project before the skill is committed. A skill documenting an invocation that
does not run is worse than no skill, because it is trusted.

`Users-antony-Development-herdr` (23,641 nodes / 97,504 edges) is a suitable
target. Note that `/Users/antony/Development/grove` itself is **not** currently
indexed, so it cannot be used as the test fixture without indexing it first.

## Non-goals

- **This does not get context7 into pi.** `@upstash/context7-mcp` is MCP-only:
  `--transport stdio|http` selects MCP-over-HTTP, not a REST surface, and there
  is no tool-invocation CLI. Nothing exists for a shell to call. Closing that
  gap requires a pi extension registering tools via `pi.registerTool()`, which
  is separate work.
- **No typed code-execution layer.** Per the research above it is a genuine
  upgrade, but it would deliver most of its value to pi (which has a native
  extension point for it) and near-none to Claude Code (where hosting it would
  mean wrapping it as an MCP server — paying MCP's per-tool schema cost to
  escape MCP's per-tool schema cost). If pursued, it is a pi-first project with
  its own spec.
- **No changes to the codebase-memory-mcp installer or its managed skill.**
